# 远期展望与可行性分析

当前版本解决的是「单账号自动维护 profile README」。下面是三个远期方向的分析——按依赖关系排序，越靠前越适合作为下一步。

## 方向一：多账号 / 组织管理

**愿景**：一个实例同时维护多个 profile 仓库（多个成员、或一个组织的总览页），并给组织一个数据面板。

**价值**：对开源组织、工作室、学生社团有真实需求——组织主页（`org/org`）自动汇总成员活跃度与明星项目。

**技术分析**：

| 子能力 | 难度 | 现有架构的复用度 |
| --- | --- | --- |
| 配置里维护 `users: [a, b, c]` 列表，循环跑现有管线 | 低 | 几乎 100%——`run()` 已参数化 username |
| 组织仓库列表（`GET /orgs/{org}/repos`） | 低 | `github_client` 加一个方法即可 |
| 组织级汇总面板（成员×star×活跃度表格） | 中 | 新增一个 Jinja2 模板 + 新指纹维度 |
| 每成员写回各自的 `a/a` 仓库 | **高** | 需要每成员的 PAT 或 GitHub App；跨仓库推送权限是最大障碍 |

**关键约束**：GitHub Actions 的内置 `GITHUB_TOKEN` 只能写当前仓库。要写 N 个成员仓库，只能：
1. 每成员配一个 PAT（管理成本随人数线性增长，Secrets 也要逐个配）；或
2. 做成 **GitHub App**（安装到组织后可代表组织向各仓库推送）——这是正路，但引入了 App 注册、私钥管理、token 自动续期一整套运维，复杂度上一个台阶。

**建议路线**：先做「只读版」——单仓库内生成一份组织汇总面板（拉多个成员数据、渲染到本仓库的 `DASHBOARD.md`），不写回成员仓库；验证价值后再考虑 GitHub App 的写回能力。

## 方向二：高级 Agent 能力（项目介绍 / 简历素材生成）

> **已实现后按用户决定移除（2026-10-24）**：产出（`docs/projects/`）非主页所需、纯耗 token——功能、配置接口、workflow 链路与产物已全部下线（git 历史可找回）。

## 方向三：项目健康度 / 依赖风险看板

**愿景**：每个账号或项目有一个健康度面板：依赖风险（已知漏洞、过期依赖）、维护状态（issue 响应、commit 活跃度、贡献者 bus factor）等。

**价值**：对工程团队是实用工具；对个人开发者更多是「主页上的可信度徽章」。

**技术分析**：

| 指标 | 数据源 | 成本 |
| --- | --- | --- |
| 依赖漏洞 | GitHub 原生 **Dependabot alerts API**（需要 repo 的 security_events 权限） | 免费但**只对有权限的仓库可用**——他人仓库拿不到 |
| 依赖过期 | 解析 lock 文件 + 对照包管理器元数据（PyPI/npm registry） | 中等；每仓库额外请求，要做缓存 |
| 维护活跃度 | 现有数据就够（push 频率、issue/PR 计数） | 低 |
| Bus factor | 贡献者分布（`GET /repos/{o}/{r}/contributors`） | 低 |

**关键约束**：Dependabot alerts 是这个方向的价值核心，但它是**权限敏感接口**——工具如果以用户 PAT 运行，只能分析用户自己有 admin 权限的仓库。做「给别人看的公开健康度」会撞上这堵墙；做「自己仓库的健康体检」则完全可行。

**建议路线**：作为独立模块 `health.py` 后期接入，先做无权限门槛的指标（活跃度、bus factor、依赖过期），漏洞检测作为「对自己的仓库」的增强功能。

## 总结：建议的演进顺序

```
当前版本（单账号 profile README）
  └─→ 方向一（只读版）：组织汇总面板
        └─→ 方向三：健康度模块（活跃度/bus factor → Dependabot）
              └─→ 方向一（写回版）：GitHub App 多仓库写回
```

三个方向共同的架构前提：**指纹缓存 + 按需生成 + 用户自带 key 控成本**。现有代码里 `aggregate.py` 的指纹机制和 `cli.py` 的增量门就是为这个演进预留的接口。
